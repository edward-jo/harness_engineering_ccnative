Agent SDK 없이 현재 실행 중인 Claude Code 환경에서 하네스 설계 방법론을 구현하는 방법 · 조사일: 2026-04-04

2. 에이전트 정의 파일 (.claude/agents/)

서브에이전트는 YAML 프론트매터 + 마크다운 시스템 프롬프트로 정의된다. Claude가 description을 보고 자동으로 위임할지 판단하거나, 명시적으로 호출할 수 있다.

기획자 — .claude/agents/planner.md
---
name: planner
description: >
  사용자의 짧은 아이디어(1~4문장)를 완전한 제품 스펙으로 확장할 때 사용.
  feature_list.json과 스프린트 계획을 생성한다.
model: opus
tools: Read, Write, Bash
color: blue
---

당신은 제품 기획자입니다. 사용자의 간략한 아이디어를 받아 다음을 생성합니다:

1. feature_list.json: 200개 이상의 세부 기능 목록
   - 각 기능: { "id", "category", "description", "steps": [], "completed": false }
2. sprint_plan.md: 스프린트별 구현 계획 (10개 스프린트)

4.1 진행 상황 자동 기록 훅

    "PostToolUse": [

        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "\".claude/hooks/progress-update.sh\"",
            "statusMessage": "진행 상황 기록 중..."
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\".claude/hooks/session-end.sh\"",
            "statusMessage": "세션 종료 처리 중..."
          }
        ]
      }
    ]
  }
}

4.2 진행 상황 기록 스크립트 (.claude/hooks/progress-update.sh)

#!/bin/bash
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // empty')

# git 커밋 감지 시 claude-progress.txt 업데이트
if echo "$COMMAND" | grep -q 'git commit'; then
  TIMESTAMP=$(date '+%Y-%m-%d %H:%M:%S')
  COMMIT_MSG=$(echo "$COMMAND" | grep -o '"[^"]*"' | head -1)
  echo "[$TIMESTAMP] 커밋: $COMMIT_MSG" >> claude-progress.txt
fi

exit 0

4.3 세션 종료 훅 (.claude/hooks/session-end.sh)

#!/bin/bash
TIMESTAMP=$(date '+%Y-%m-%d %H:%M:%S')
echo "[$TIMESTAMP] 세션 종료" >> claude-progress.txt

if [ -f "feature_list.json" ]; then
  TOTAL=$(jq '[.[]] | length' feature_list.json 2>/dev/null || echo "?")
  DONE=$(jq '[.[] | select(.completed == true)] | length' feature_list.json 2>/dev/null || echo "?")
  echo "  진행: $DONE/$TOTAL 기능 완료" >> claude-progress.txt
fi

exit 0

5. 슬래시 커맨드 (.claude/commands/)

/harness 커맨드

하네스를 시작합니다. 다음 절차로 진행하세요:

1. **planner 에이전트**를 사용해서 "$ARGUMENTS"를 완전한 제품 스펙으로 확장하고
   feature_list.json과 sprint_plan.md를 생성하세요.

2. 기획 완료 후 다음 단계 안내:
   - `/sprint 1` - 스프린트 1 시작
   - `/sprint review` - 현재 스프린트 평가

/sprint 커맨드

스프린트를 관리합니다. $ARGUMENTS에 따라:

- **숫자** (예: `1`, `3`): generator 에이전트를 사용해서 해당 스프린트 구현
- **review**: evaluator 에이전트를 사용해서 현재 스프린트 검증
- **status**: feature_list.json 읽어서 전체 진행 상황 리포트

8. 루프(반복 실행) 구현

Claude Code 네이티브에서 루프는 3가지 방식으로 구현한다.

방식 A: Stop 훅 기반 자동 루프 (가장 강력)

Claude가 응답을 완료할 때 Stop 훅이 실행되고, 검증 실패 시 decision: "block"으로 Claude를 재실행시킨다.

동작 원리

Claude 응답 완료
      │
      ▼
[Stop 훅 실행]
  → loop-guard.sh 실행
  → sprint_result.json 검사
      │
      ├─ FAIL + 횟수 < MAX → decision: "block" → Claude 재실행
      └─ PASS 또는 횟수 >= MAX → exit 0 → 정상 종료

.claude/settings.json 훅 설정

{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\".claude/hooks/loop-guard.sh\"",
            "timeout": 30
          }
        ]
      }
    ]
  }
}

.claude/hooks/loop-guard.sh

#!/bin/bash
INPUT=$(cat)
LOOP_COUNT_FILE=".claude/loop_count.txt"
MAX_LOOPS=15

COUNT=$(cat "$LOOP_COUNT_FILE" 2>/dev/null || echo 0)

# 최대 횟수 초과 시 강제 종료
if [ "$COUNT" -ge "$MAX_LOOPS" ]; then
  echo 0 > "$LOOP_COUNT_FILE"
  exit 0
fi

# sprint_result.json 확인 (evaluator가 기록)
if [ -f "sprint_result.json" ]; then
  STATUS=$(jq -r '.status' sprint_result.json 2>/dev/null)

  if [ "$STATUS" = "FAIL" ]; then
    FAILS=$(jq -r '.failures | join(", ")' sprint_result.json)
    NEW_COUNT=$((COUNT + 1))
    echo "$NEW_COUNT" > "$LOOP_COUNT_FILE"

    jq -n \
      --arg reason "[$NEW_COUNT/$MAX_LOOPS] 검증 실패: $FAILS. generator 에이전트로 수정 후 evaluator로 재검증하세요." \
      '{
        "decision": "block",
        "reason": $reason
      }'
    exit 0
  fi
fi

# PASS → 정상 종료
echo 0 > "$LOOP_COUNT_FILE"
exit 0

evaluator가 기록하는 sprint_result.json 포맷

evaluator 에이전트 시스템 프롬프트에 다음 지시 추가:

# PASS 시
{ "status": "PASS", "passed": 27, "total": 27, "failures": [] }

# FAIL 시
{ "status": "FAIL", "passed": 25, "total": 27,
  "failures": ["fillRectangle mouseUp 미트리거", "422 에러 발생"] }

방식 B: 코디네이터 에이전트 프롬프트 루프

별도 코디네이터 에이전트가 generator → evaluator 루프를 자체적으로 반복 수행한다.

.claude/agents/coordinator.md

---
name: coordinator
description: >
  하네스 전체 루프를 자율 실행할 때 사용.
  generator와 evaluator를 반복 호출해 스프린트를 완성한다.
model: opus
tools: Agent(generator, evaluator), Read, Write, Bash
maxTurns: 50
color: purple
---

당신은 하네스 코디네이터입니다. 다음 루프를 실행합니다:

반복 횟수 = 0 / 최대 반복 = 15

LOOP:
  1. generator 에이전트 호출: "sprint_contract.md 기반으로 스프린트 구현"
  2. evaluator 에이전트 호출: "sprint_contract.md 기준을 Playwright로 검증"
  3. evaluator 결과 확인:
     - 모두 PASS → 루프 종료
     - FAIL + 횟수 < 최대 → 반복 횟수 += 1, LOOP 재실행
     - FAIL + 횟수 >= 최대 → 사용자에게 수동 개입 요청

호출 방법

# coordinator 에이전트가 알아서 루프 실행
"coordinator 에이전트를 사용해서 스프린트 3을 완료할 때까지 반복 실행해줘"

# 슬래시 커맨드
/sprint auto 3

방식 C: 프론트엔드 디자인 반복 루프 (5~15회)

원본 아티클의 프론트엔드 디자인 반복 루프. design-generator와 design-evaluator를 반복 호출해 미학 점수를 높인다.

.claude/agents/design-loop.md

---
name: design-loop
description: >
  프론트엔드 UI를 반복적으로 개선할 때 사용.
  5~15회 반복해 미학 점수를 높인다.
model: opus
tools: Agent(design-generator, design-evaluator), Read, Write, Bash
maxTurns: 60
color: pink
---

반복 횟수 = 0 / 최소 = 5 / 최대 = 15 / 목표 점수 = 80

LOOP:
  1. design-generator 호출: 첫 번째는 새 방향, 이후는 피드백 반영
  2. design-evaluator 호출: 4가지 기준 채점 (100점 만점)
  3. 점수 확인:
     - 반복 < 최소 → 무조건 계속
     - 점수 >= 80 AND 반복 >= 최소 → 종료
     - 반복 >= 최대 → 최고 점수 버전으로 되돌리고 종료
     - direction = "pivot" → 완전히 새로운 미학으로 전환

.claude/agents/design-evaluator.md

---
name: design-evaluator
description: 프론트엔드 UI를 4가지 기준으로 평가하고 점수를 매길 때 사용
model: sonnet
tools: Bash, Read
mcpServers:
  - playwright:
      type: stdio
      command: npx
      args: ["-y", "@playwright/mcp@latest"]
permissionMode: plan
color: yellow
---

방식별 비교

방식자동화 수준루프 제어 위치적합한 경우
A. Stop 훅완전 자동셸 스크립트스프린트 검증 반복
B. 코디네이터 에이전트완전 자동에이전트 프롬프트복잡한 조건 분기
C. design-loop완전 자동에이전트 프롬프트프론트엔드 미학 개선
수동 /sprint review수동사용자한 번씩 검증

무한 루프 방지 체크리스트

  • maxTurns 설정: 코디네이터 에이전트에 반드시 적용
  • Stop 훅 카운터: loop_count.txt로 횟수 추적
  • stop_hook_active 확인: Stop 훅 내에서 재귀 방지
  • 명시적 종료 조건: PASS 또는 최대 횟수 도달 시 exit 0

9. 모델별 하네스 단순화 전략

모델권장 하네스 구성
Sonnet 4.5스프린트 계약 + 반복 evaluator 필수 (컨텍스트 불안감)
Opus 4.5스프린트 구조 유지, evaluator 간소화 가능
Opus 4.6스프린트 제거 가능, evaluator를 단일 최종 패스로 변경
각 하네스 구성 요소는 "모델이 독립적으로 할 수 없다"는 가정을 인코딩한다. 모델 업데이트마다 불필요한 스캐폴딩을 제거하고 새로운 기능을 추가한다.
