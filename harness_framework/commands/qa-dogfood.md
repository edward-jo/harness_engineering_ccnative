---
description: 웹 앱(Playwright) 또는 모바일 앱(Maestro)을 실사용자처럼 전 화면 dogfood 테스트하고 발견된 문제를 GitHub issue로 등록한다. 자동화 도구는 --mcp로 지정하거나 시작 시 선택한다. 인자로 특정 화면(범위)을 지정할 수 있다.
argument-hint: "[--mcp=playwright|maestro] [테스트 범위 — 경로/화면이름, 쉼표구분, 비우면 전체]"
---

역할: 너는 이 앱을 실제 사용자처럼 직접 써 보는 QA 엔지니어다. 화면을 하나씩
dogfood 테스트하고, 발견하는 모든 문제를 GitHub issue로 등록하라. 대상 화면
테스트가 끝날 때까지 반복한다. 웹 앱은 Playwright MCP로, 모바일 앱은 Maestro
MCP로 조작한다.

인자 = $ARGUMENTS

== 자동화 도구(MCP) 결정 — 0단계보다 먼저 ==
- `$ARGUMENTS`에서 `--mcp=playwright` 또는 `--mcp=maestro` 토큰을 파싱한다. 이
  토큰은 테스트 범위에서 제외하고, 나머지를 "테스트 범위(scope)"로 본다.
- `--mcp`가 주어졌으면 그 자동화 도구로 확정하고 질문하지 않는다.
- `--mcp`가 없으면:
    * `.claude/stack.md`의 "플랫폼 & E2E 환경" 표에 "dogfood 기본 자동화 도구"가
      지정돼 있으면 그 값을 추천값으로 삼되, 진행 전에 사용자에게
      "이번 dogfood를 Playwright(웹)로 할까요, Maestro(모바일)로 할까요?"
      라고 묻고 답을 받은 뒤 진행한다.
    * stack.md 기본값도 없으면 동일하게 사용자에게 묻고, 답을 받기 전까지
      진행하지 않는다(임의로 web을 가정하지 말 것).
- 선택한 자동화 도구의 MCP 툴이 현재 세션에 연결돼 있는지 먼저 확인한다.
    * playwright: 플러그인 `.mcp.json`에 기본 등록돼 있어 보통 바로 사용 가능.
    * maestro: 선택적 등록이다. Maestro MCP 툴이 보이지 않으면 아래를 안내하고
      **멈춘다**(브라우저로 폴백하거나 추측으로 진행하지 말 것):
        - `claude mcp add maestro -- maestro mcp` 로 Maestro MCP 등록
        - Maestro CLI 설치 + 안드로이드 에뮬레이터/iOS 시뮬레이터 부팅 + 대상
          앱(apk/app) 설치 + appId 확인이 선행돼야 함
      준비되면 다시 실행해 달라고 사용자에게 알린다.

== 자동화 도구 능력 매핑 (이하 모든 단계에서 "능력"은 선택한 자동화 도구로 해석) ==
| 능력 | 웹(Playwright MCP) | 모바일(Maestro MCP) |
|------|--------------------|----------------------|
| 진입/실행 | `browser_navigate` | `launch_app` (appId) |
| 화면 상태 스냅샷 | `browser_snapshot` | `inspect_view_hierarchy` |
| 클릭/탭 | (요소 클릭) | `tap_on` |
| 텍스트 입력 | `browser_type` | `input_text` |
| 스크린샷(증거) | `browser_take_screenshot` | `take_screenshot` |
| 멀티스텝 흐름 | (순차 조작) | `run_flow` (인라인 YAML) |
| 콘솔 에러 | `browser_console_messages` | ⚠️ 라이브 불가 — `maestro.log`/리포트로 사후 확인 |
| 네트워크 4xx·5xx | `browser_network_requests` | ⚠️ 라이브 불가 — YAML `http.*()` 수동 검사 또는 제외 |
(Maestro 실제 툴 이름이 위와 다르면 `cheat_sheet`로 확인해 맞춘다.)

== 0. 사전 파악 (코드/문서에서 직접 알아낼 것) ==
- 앱 실행 방법 (자동화 도구별):
    * web(Playwright): README / CLAUDE.md / package.json scripts 에서 dev 서버
      기동 명령과 포트를 찾는다. 백엔드/DB가 따로 필요하면 같이 띄우는 방법과
      시드 데이터 적재 방법도 찾는다.
    * mobile(Maestro): `.claude/stack.md`의 "플랫폼 & E2E 환경"에서 appId,
      에뮬레이터/시뮬레이터 기동 명령, 앱(apk/app) 설치 방법을 찾는다. 없으면
      package.json의 react-native/expo/flutter 의존성·스크립트나 `ios/`·
      `android/` 디렉토리로 추론하고, 그래도 불명확하면 사용자에게 묻는다.
- 로그인 계정: 시드/테스트 계정을 코드에서 찾는다(seeder, .env.example, docs).
- 테스트 대상 화면 결정:
    * 테스트 범위(scope)가 지정됐으면 → 그 화면들만 대상으로 한다. 지정값이
      경로면 그대로, 화면/탭 이름이면 라우터·네비에서 해당 경로로 매핑한다.
      범위 밖 화면은 테스트하지 않는다.
    * 범위가 비어 있으면 → 전체를 대상으로 한다. web이면 라우터 정의(예:
      src/app, router 설정, 네비게이션 메뉴)에서, mobile이면 네비게이션/스크린
      정의(예: React Navigation 라우트, 화면 테이블)에서 모든 경로/화면 이름을
      추출한다.

== 1. 환경 기동 & 스모크 ==
- web: 앱(필요 시 백엔드/DB 포함)을 기동하고 헬스/접속을 확인한다.
- mobile: 에뮬레이터/시뮬레이터를 부팅하고 대상 앱을 설치한 뒤 실행(launch_app)한다.
- 선택한 자동화 도구로 첫 화면에 진입해 로그인에 성공하고 첫 화면을 스냅샷한다.
- 실패하면 멈추지 말고 원인(포트 충돌, 시드 누락, 환경변수, 에뮬레이터 미부팅,
  앱 미설치, appId 오류)을 찾아 해결한 뒤 진행한다. 해결 불가하면 사용자에게
  구체적으로 무엇이 막혔는지 보고한다.

== 2. 화면별 dogfood 체크리스트 (각 화면마다) ==
실사용자처럼 다음을 수행하고, 각 단계에서 이상을 관찰한다(도구는 위 능력 매핑표
대로 선택한 자동화 도구로 해석):
  (a) 진입 & 렌더 — 진입 후 스냅샷. 빈 화면/무한 스피너 확인.
      * web: 콘솔 에러(`browser_console_messages`)·네트워크 4xx·5xx
        (`browser_network_requests`)도 확인.
      * mobile: 라이브 콘솔/네트워크 관찰은 불가하다. `maestro.log`·리포트로
        사후 확인하거나, 해당 점검을 명시적으로 제외하고 그 사실을 보고에 남긴다.
  (b) 데이터 읽기 — undefined / NaN / [object Object] / 깨진 표·빈 목록 등
      필드 드리프트 징후 확인.
  (c) 핵심 작업(편집 화면) — 생성→수정→삭제→정렬 등 실제 조작. 각 작업 후
      화면 즉시 반영 + 새로고침/재진입 후에도 유지되는지.
  (d) 멀티스텝 플로우 — 저장/발행/제출 등 여러 화면을 잇는 핵심 흐름이
      끝까지 성공하는지.
  (e) 경계/오류 — 필수값 누락 제출, 잘못된 입력, 권한 없는 동작이 그레이스풀
      하게 처리되는지(앱이 죽지 않는지).
  (f) 증거 — 결함을 보면 스크린샷(능력: 스크린샷)으로 정상/이상 상태를 캡처.
읽기 전용 화면은 (a)(b)(e)만, 편집 화면은 전부 수행한다.

== 3. 결함 → GitHub issue 등록 ==
- 한 화면 테스트가 끝나면, 모인 결함을 GitHub issue로 등록한다.
- harness:file-issue 스킬이 있으면 그것을 쓴다(중복 방지 + 스크린샷을
  harness-assets 브랜치에 push 후 raw URL로 본문 임베드). 없으면 gh CLI로:
    * 등록 전 `gh issue list --state open --search "<핵심 키워드>"` 로 중복 확인.
    * `gh issue create --title "[QA] <화면>: <요약>" --label qa,manual-finding
      --body "<증상/기대동작/재현단계/관련경로/스크린샷>"`.
    * 본문 맨 끝에 dedup 주석 `<!-- qa-dogfood key=<screen>/<slug> -->` 을 넣어
      재실행 시 같은 키 검색으로 중복을 막는다.
- issue 본문 필수 섹션: ## 증상 / ## 기대 동작 / ## 재현 절차 / ## 관련 파일
  / (스크린샷 임베드).
- 등록 방식 기본값은 "화면 단위로 모아서 등록"이다. 사용자가 자동 등록을
  지시했으면 확인 없이 등록한다.

== 4. 반복 & 완료 조건 ==
- 0번에서 정한 대상 화면 목록을 처음부터 끝까지 순서대로 진행한다(범위 미지정
  시 최근 변경/핵심 기능 화면 우선).
- 진행 상태를 TaskCreate/TaskUpdate 로 화면별 추적(테스트 완료 / 등록 N건).
- 대상 화면이 전부 "테스트 완료"가 되고 발견된 모든 결함이 issue로 등록(또는
  의도적 제외 기록)될 때까지 멈추지 않는다. 길어지면 화면 단위로 재개한다.

== 5. 최종 보고 ==
- 화면별 결과표(통과 / 결함 N) + 등록한 issue 번호 목록 + 보류 항목을 정리해
  보고한다. Maestro(모바일)였다면 라이브 콘솔/네트워크 미관찰로 제외한 점검
  항목도 함께 명시한다.

원칙: 추측으로 "정상"이라 적지 말 것. 실제로 조작·관찰한 것만 보고한다.
선택한 자동화 도구만 사용하고, 자동화 도구 미선택·MCP 미연결 상태로는 진행하지
말 것. 앱을 수정하지 말 것(테스트만 한다). 발견을 과장하거나 누락하지 말 것.
